# Keamanan

- URL input/output, URL Stream View, dan konfigurasi PTZ sensitif disimpan dengan AES-256-GCM menggunakan `APP_ENCRYPTION_KEY`.
- URL Stream View dibatasi ke HTTP/HTTPS, tidak boleh memuat embedded credential, dan dapat dibatasi melalui `STREAM_VIEW_ALLOWED_ORIGINS`. HTTP direct-source default-nya nonaktif.
- URL Stream View tersimpan divalidasi ulang terhadap kebijakan terbaru setiap kali daftar Viewer dimuat. Stream View yang tidak lolos (mis. dibuat saat development atau sebelum allowlist origin dipasang) dilewati dan dicatat sebagai warning dengan ID stream saja, tanpa URL, sehingga kamera lain tetap tampil.
- Endpoint file MP4 Viewer menangani `HEAD` secara eksplisit: hanya metadata file yang dibaca, sehingga `HEAD` tidak dapat dipakai untuk memicu pembacaan seluruh file dari disk.
- Sumber MP4 File Server hanya dapat dipilih Admin, harus berupa path absolute menuju file `.mp4` yang readable, dan disimpan terenkripsi. Viewer hanya menerima URL proxy same-origin; path filesystem server tidak diekspos melalui DTO Viewer.
- Password Administrator dan Operator disimpan sebagai bcrypt hash. Nilai `.env` hanya dipakai saat bootstrap pertama; perubahan dari Settings mengganti hash secara atomik dan merotasi versi credential untuk mencabut seluruh sesi lama role terkait.
- Session menggunakan token HMAC dalam cookie HTTP-only dan SameSite Strict. Atribut Secure diatur `COOKIE_SECURE`: bila tidak diisi, Secure hanya dipasang saat `NODE_ENV=production` (perilaku lama); `auto` memasang Secure hanya untuk request yang tiba lewat HTTPS; `true`/`false` memaksa. Nilai lain ditolak saat startup. Atribut yang sama dipakai saat logout menghapus cookie, karena browser mengabaikan `Set-Cookie` ber-Secure yang dikirim lewat HTTP biasa.
- `COOKIE_SECURE=auto` (default container Docker) diperlukan bila dashboard dibuka lewat `http://<IP LAN>:3000`: browser tidak menyimpan atau tidak mengirim cookie Secure lewat HTTP biasa (kecuali `localhost`), sehingga login tampak berhasil tetapi sesi langsung hilang. Mode `auto` membaca `request.protocol`; header `X-Forwarded-Proto` hanya dipercaya dari proxy yang terdaftar di `TRUST_PROXY`, jadi client langsung tidak dapat mengklaim HTTPS. Di belakang reverse proxy TLS, atur `TRUST_PROXY` agar cookie tetap Secure. Untuk akses di luar LAN tepercaya, tetap gunakan HTTPS.
- Setiap session Administrator/Operator membawa versi credential yang harus cocok dengan nilai acak `auth.<role>.credentialVersion` di database. Startup membuat versi acak bila belum ada (database baru maupun backup lama), dan login membuatnya kembali bila baris tersebut hilang. Tanpa versi tersimpan, session role tersebut selalu ditolak (fail closed), sehingga `AUTH_SECRET` saja tidak cukup untuk memalsukan session Administrator/Operator. Startup pertama setelah pembaruan ini mengeluarkan session lama yang belum memiliki versi.
- Viewer tidak memakai password dan tetap memakai versi `0`; cookie Viewer palsu tidak memberi akses melebihi login Viewer biasa.
- Masa hidup session dibatasi server maksimal 24 jam. Token dengan `exp` lebih jauh dari batas itu ditolak walau signature valid.
- Logout hanya menghapus cookie di browser. Token yang sempat tersalin tetap berlaku sampai `exp`; cabut seluruh session role dengan mengganti password dari Settings atau `npm run auth:reset`.
- Bila `AUTH_SECRET` bocor, ganti nilainya lalu restart API. Semua session lama menjadi tidak valid.
- Semua command FFmpeg dibentuk sebagai array argumen allowlist dan dijalankan melalui `spawn` dengan `shell: false`.
- Arbitrary FFmpeg argument dan shell command tidak diterima API.
- Credential di-redact sebelum log ditulis dan DTO API hanya mengirim URL yang sudah di-mask.
- Untuk URL RTMP/RTMPS, stream key ikut di-mask di DTO route (`outputsMasked`, `inputUrlMasked`), command FFmpeg yang dicatat, dan log route: segmen path terakhir diganti `***` bila path memiliki minimal dua segmen, serta seluruh query/fragment diganti `***`, mis. `rtmp://a.rtmp.youtube.com/live2/***`. Host, port, dan path app tetap terbaca agar output dapat dibedakan. URL plaintext hanya tersedia bagi Admin melalui endpoint edit route.
- Untuk URL kamera (RTSP) dan link WebRTC, query yang namanya memuat `pass`, `pwd`, `secret`, `token`, `key`, `auth`, `sig`, atau `jwt` di-mask. Segmen path yang memuat `password=`, `passwd=`, `pass=`, atau `pwd=` (format XMEye/ICSee seperti `/user=admin&password=X&channel=1` atau `/user=admin_password=X_channel=1`) diganti `***` seluruhnya.
- URL stream yang tidak dapat di-parse (mis. password kamera berisi `#`, `?`, atau `/` yang belum di-encode) ditolak `400 INVALID_STREAM_URL` tanpa menyertakan URL mentah, sehingga password tidak ikut tercatat di log error.
- Percobaan password Administrator/Operator dibatasi 5 per menit per IP client; endpoint lain memiliki rate limit global. Login Viewer (tanpa password, tanpa bcrypt) memakai batas terpisah 60 per menit per IP, sehingga banyak layar monitor tidak menghabiskan jatah login Administrator.
- Login Administrator/Operator yang berhasil memasang cookie perangkat `stream_router_login_device` (HTTP-only, SameSite Strict, path `/api/auth/login`, 30 hari, ditandatangani kunci turunan `AUTH_SECRET` yang berbeda dari kunci sesi). Cookie ini bukan sesi dan tidak membuka endpoint apa pun; browser yang membawanya memakai bucket rate limit login sendiri dan jalur antrean bcrypt terpisah yang dilayani lebih dulu, sehingga banjir percobaan dari perangkat lain tidak membuat loginnya ditolak `RATE_LIMITED` atau `LOGIN_BUSY`. Cookie perangkat ikut dicabut saat password role tersebut diganti. Kepercayaan sengaja tidak berbasis IP: di Docker Desktop semua klien LAN terlihat dari satu IP gateway.
- Verifikasi bcrypt dijalankan satu per satu dengan antrean terbatas agar percobaan login serentak tidak menahan event loop. Penolakan `LOGIN_BUSY` tidak dihitung dalam rate limit login pemanggil.
- Batasan di balik NAT bersama (mis. Docker Desktop di Windows/macOS): semua klien tanpa cookie perangkat berbagi satu bucket 5/menit, sehingga perangkat mana pun di LAN dapat membuat login password dari browser lain yang belum pernah login (atau cookie-nya kedaluwarsa/dicabut) terus dijawab `429 RATE_LIMITED` hanya dengan 5 request per menit. Sesi yang sudah berjalan, login Viewer, dan browser dengan cookie perangkat yang valid tidak terpengaruh. Rate limit berbasis IP maupun role tidak dapat mencegah hal ini sepenuhnya; batasi akses port 3000 ke LAN tepercaya.
- `TRUST_PROXY=true` hanya mempercayai reverse proxy di host yang sama (loopback); proxy lain harus disebut sebagai IP/CIDR. Reverse proxy wajib menimpa `X-Forwarded-For` agar header kiriman client tidak dapat mengganti IP untuk rate limit.
- Pada production, request state-changing (`POST`/`PATCH`/`PUT`/`DELETE`, kecuali login) yang membawa header `Origin` hanya diterima bila Origin sama dengan `CORS_ORIGIN` atau sama dengan alamat yang dipakai untuk membuka server itu sendiri (`request.protocol` + header `Host`, mis. `http://192.168.1.10:3000` saat dashboard dibuka dari host lain di LAN). Origin lain ditolak `403 CSRF_ORIGIN_REJECTED`. Header `Host` yang bukan bentuk `host[:port]` tidak pernah dianggap origin yang sama.
- DNS rebinding (halaman penyerang me-resolve domainnya ke IP server lalu memanggil API sebagai same-origin) dicegah allowlist header `Host` yang diperiksa pada production sebelum route apa pun berjalan, termasuk `GET`, file statis, dan login. Pemeriksaan origin saja tidak cukup: Origin dan Host request seperti itu sama-sama domain penyerang, login Viewer tidak memerlukan password, dan dengan `COOKIE_SECURE=auto` lewat HTTP browser menyimpan cookie sesi untuk domain penyerang. Host yang diterima: IP literal (IPv4/IPv6), `localhost`, hostname `CORS_ORIGIN`, hostname `MEDIAMTX_PUBLIC_HOST`, dan daftar `ALLOWED_HOSTS` (dipisah koma, tanpa skema dan port, mis. `ALLOWED_HOSTS=PC-KAMERA,kamera.local` untuk nama komputer Windows atau nama `.local`). Host lain ditolak `421 HOST_NOT_ALLOWED` tanpa cookie. Akses lewat IP LAN, `localhost`, healthcheck container, dan hook segment MediaMTX (`127.0.0.1`) tidak terpengaruh. Di belakang reverse proxy yang meneruskan `Host` asli (`proxy_set_header Host $host`), hostname publik cukup diisi di `CORS_ORIGIN`.
- Error production tidak menampilkan stack trace maupun teks error internal. Semua error API memakai envelope `{ error: { code, message, details, requestId } }`.
- `/api/health` dan `/api/ready` tanpa sesi Administrator/Operator hanya mengembalikan status ringkas; versi binary, port, path storage, memori proses, dan teks error tidak dikirim. `/api/ready` yang gagal hanya menyebut nama pemeriksaannya (mis. `mediaMtx.recordingStorage`); teks error yang sudah diredaksi ditulis ke log server.
- Stream SSE `/api/events` memeriksa ulang sesi setiap heartbeat, dibatasi per sesi dan per IP, dan bagi Viewer hanya membawa status route yang tampil di monitor tanpa detail error.
- Endpoint konfigurasi PTZ hanya dapat diakses admin. Viewer/operator hanya dapat mengirim perintah ke ID target yang sudah tersimpan, aktif, terlihat di Viewer, dan memiliki PTZ enabled.
- Endpoint ONVIF discovery, inspect, dan import hanya dapat diakses Admin serta memiliki rate limit. Scan memakai WS-Discovery multicast tanpa CIDR/port sweep; handshake kamera diserialkan satu per satu.
- Credential dan RTSP URI bercredential dari wizard ONVIF hanya disimpan pada session memori sementara, tidak dikirim kembali ke browser, dibersihkan setelah import/timeout/shutdown, dan tidak dimasukkan ke audit atau log.
- Backend PTZ memakai queue per kamera dan dead-man stop untuk membatasi risiko gerakan berlanjut ketika event release dari browser hilang. Queue hanya menahan satu perintah tertunda per kamera (perintah terbaru menang), sehingga stop tidak tertahan di belakang keepalive yang menumpuk; dead-man dihitung dari kedatangan perintah terakhir dan tetap aktif walaupun keepalive gagal terkirim.
- Mengubah protocol, host, atau port profil broker MQTT yang sudah memiliki password mewajibkan password diketik ulang, agar password tersimpan tidak terkirim ke endpoint baru.
- Status `CONNECTED` PTZ hanya diberikan setelah handshake ONVIF/MQTT berhasil atau perintah berhasil dikirim. Status bersifat runtime dan kembali `UNTESTED` setelah API restart agar hasil lama tidak dianggap sebagai koneksi aktif.
- Control API MediaMTX, playback, dan metrics bind ke localhost. Credential kamera dikirim melalui Control API lokal dan tidak ditulis ke YAML.
- Bila dashboard dibuka lewat HTTPS, player WebRTC lokal harus disajikan reverse proxy HTTPS (`MEDIAMTX_WEBRTC_PUBLIC_URL`) agar tidak diblokir sebagai mixed content dan signaling WHEP tidak lewat HTTP biasa. URL itu hanya dibaca dari `.env` dan tidak dapat diubah dari dashboard. Koneksi proxy tidak boleh tiba di MediaMTX dari loopback (mis. nginx native ke `127.0.0.1:18889`), karena `127.0.0.1`/`::1` mendapat izin baca dan publish untuk semua path sehingga Local Media OFF terlewati; lihat [DEPLOYMENT.md](DEPLOYMENT.md#webrtc-lewat-https).
- Local Media OFF melepas izin read anonim untuk path tersebut; localhost tetap mendapat izin read agar relay online dapat berjalan.
- Playback/download recording selalu melewati backend dan role check. Path filesystem serta credential tidak dikirim dalam DTO recording.
- Hook segment MediaMTX (`/internal/mediamtx/segments`) hanya menerima koneksi dari socket loopback (bukan alamat `X-Forwarded-For`) dengan token HMAC yang diturunkan dari `AUTH_SECRET`; `AUTH_SECRET` sendiri tidak dikirim lewat header. Request dari reverse proxy di host yang sama tetap berasal dari loopback, jadi blokir `/internal/` di proxy seperti contoh Nginx pada [DEPLOYMENT.md](DEPLOYMENT.md).
- MediaMTX binary development diverifikasi dengan SHA-256 release resmi sebelum dieksekusi.

## SSRF

Private IP tidak diblokir secara default karena kamera dan broker MQTT biasanya berada di LAN. Konsekuensinya, admin yang memiliki akses dashboard dapat meminta server menghubungi host internal melalui URL stream, ONVIF, atau MQTT. Mitigasi deployment:

1. Batasi akses dashboard ke VPN/VLAN admin.
2. Terapkan egress firewall hanya ke subnet kamera dan endpoint streaming yang diperlukan.
3. Tambahkan daftar deny-host pada extension point `assertSsrfPolicy` bila jaringan memerlukan pembatasan tambahan.
4. Jangan mengekspos control plane langsung ke internet tanpa HTTPS dan autentikasi tambahan di reverse proxy.

## Rotasi key

Jangan mengganti `APP_ENCRYPTION_KEY` langsung. Data yang sudah terenkripsi hanya dapat dibuka dengan key lama: route auto-start gagal saat boot, serta endpoint route, MQTT broker, PTZ, dan Stream View mengembalikan error. Gunakan `npm run secrets:reencrypt` untuk mengenkripsi ulang seluruh kolom `*Encrypted` (`StreamRoute`, `WebrtcStream`, `MqttBroker`) dalam satu transaksi:

1. Hentikan API (`pm2 stop stream-router` atau `Ctrl+C` pada `npm run dev`). MediaMTX tidak membaca database sehingga tidak perlu dihentikan; kamera tetap direkam, tetapi tanpa retention dan storage guard sampai API berjalan lagi, jadi jangan biarkan API mati lama.
2. Salin nilai `APP_ENCRYPTION_KEY` lama ke tempat aman sementara, misalnya password manager. Buat key baru dengan `npm run secrets:generate`, lalu ganti baris `APP_ENCRYPTION_KEY` di `.env`. Bila `.env` ikut bocor, ganti juga secret lain sesuai bagian berikut.
3. Jalankan `npm run secrets:reencrypt -- --dry-run`, masukkan key lama pada prompt tersembunyi, dan pastikan kolom gagal bernilai 0. Tanda `--` wajib; tanpa itu npm menelan `--dry-run` dan script menolak berjalan.
4. Jalankan `npm run secrets:reencrypt`. Script menolak berjalan bila port API masih aktif atau bila variabel shell berbeda dengan `.env`. Script membuat backup SQLite di folder `backups/` di samping database (permission 600), menulis dan memverifikasi seluruh nilai sebelum commit, lalu menjalankan `VACUUM` agar sisa ciphertext key lama terhapus dari file database aktif. Bila satu nilai gagal, tidak ada data yang diubah.
5. Jalankan aplikasi, lalu periksa route, MQTT broker, PTZ, dan Stream View.
6. Setelah terverifikasi, hapus backup dari langkah 4 dan semua salinan lama yang masih dapat didekripsi dengan key lama: `data/backups/*.db`, `backups/` di root project (termasuk `pre-upgrade.db` dan `pre-upgrade.env`), serta salinan `.env` seperti `.env.save`.

Key lama dibaca dari prompt tersembunyi atau environment `OLD_APP_ENCRYPTION_KEY`, tidak pernah dari argumen command, agar tidak tersimpan di shell history. Script aman dijalankan ulang: nilai yang sudah memakai key baru dilewati dan `VACUUM` diulang.

**Rollback** bila aplikasi bermasalah setelah rotasi: hentikan API, salin backup dari langkah 4 ke `data/stream-router.db`, lalu jalankan ulang `npm run secrets:reencrypt` dengan key lama pada prompt (key baru tetap di `.env`). Alternatifnya, kembalikan key lama ke `.env`. Jangan memulihkan backup lama tanpa salah satu langkah tersebut karena isinya terenkripsi dengan key lama.

### Bila `.env` bocor

File `.env` yang bocor juga membuka secret lain. Ganti semuanya, bukan hanya `APP_ENCRYPTION_KEY`:

- `AUTH_SECRET` menandatangani cookie sesi. Siapa pun yang memegangnya dapat membuat cookie Viewer palsu, dan cookie Administrator/Operator palsu bila versi credential dari satu cookie sah ikut diketahui. Ganti dengan nilai baru dari `npm run secrets:generate` lalu restart API dan MediaMTX agar hook recording memakai nilai baru; seluruh pengguna perlu login ulang.
- `ADMIN_PASSWORD` dan `OPERATOR_PASSWORD`: isi nilai baru di `.env`, lalu jalankan `npm run auth:reset -- --role all`. Mengubah `.env` saja tidak mengganti password yang tersimpan. Perintah ini juga mencabut seluruh sesi lama.
- `APP_ENCRYPTION_KEY`: rotasi dengan langkah di atas. Rotasi beserta `VACUUM` melindungi salinan database berikutnya, tetapi salinan database atau backup yang sudah beredar tetap dapat dibuka. Bila salinan seperti itu mungkin bocor, ganti juga credential asalnya: password kamera/ONVIF, password MQTT broker, dan stream key RTMP.
- Bila file pernah di-commit, anggap seluruh isinya publik walaupun history sudah dibersihkan.

Backup `.env` secara terenkripsi dan terpisah dari database.
